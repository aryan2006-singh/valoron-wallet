# SECURITY.md

## Part A — Attack your own system

### 1. A logged-in user tries to send money from someone else's wallet.
**Attack:** call `POST /api/support` (or `send_support` directly) with `senderId` set to someone else's user id, while authenticated as themselves.
**Stopped by:** the API route (`src/app/api/support/route.ts`) never accepts a sender id from the client — it always uses `supabase.auth.getUser()` server-side. Even if the RPC were called directly, `send_support` (`supabase/migrations/20260803174851_money_functions.sql`) checks `if auth.uid() is distinct from p_sender_id then raise ... errcode 'P1002'` as its first statement, before touching any table. `IS DISTINCT FROM`, not `<>`, so an *unauthenticated* caller (`auth.uid()` is `null`) posing as anyone is also correctly rejected — a plain `<>` comparison against `null` would silently evaluate to `null`/false and let the check pass.

### 2. A logged-in user tries to release someone else's escrow hold.
**Attack:** call `POST /api/escrow/release` with someone else's `holdId`.
**Stopped by:** `release_escrow` reads the hold's own `funder_id` first, then checks `auth.uid() is distinct from v_hold.funder_id`, raising `P1002` before any lock or balance change. Ownership comes from the row itself, never from a client-supplied field.

### 3. A logged-in user tries to credit their own wallet without paying.
**Attack:** expect `/api/deposit/intent` to move money by itself; replay/guess an `intent_id` at `/api/webhooks/payment`; call `credit_deposit` directly via `supabase.rpc()` from the browser.
**Stopped by three independent layers:** (a) `create_deposit_intent` only ever inserts a `'pending'` row and returns an id — there is no code path from it to a balance change. (b) `credit_deposit` is `REVOKE`d from `PUBLIC` and `GRANT`ed only to `service_role` — calling it with the browser's publishable key gets a Postgres permission-denied error before the function body runs at all. (c) the one caller that *can* reach it — our webhook route — only calls it after `verifySignature()` passes against the raw body using `PAYMENT_WEBHOOK_SECRET`, a server-only env var never bundled to the client.

### 4. Someone with only the public anon key tries to write directly to `ledger_entries`, `account_balances`, or `withdrawal_requests`.
**Attack:** `POST /rest/v1/ledger_entries` (or the others) with the publishable key.
**Stopped by:** `20260803174328_rls_and_grants.sql` does `revoke all ... from anon` on every financial table and grants `authenticated` `SELECT` only — never write. `anon` has zero privileges at the Postgres grant level, rejected before RLS is even evaluated. `ledger_entries` additionally has `ledger_entries_no_update` / `_no_delete` triggers that unconditionally reject `UPDATE`/`DELETE`, so even a role with a write grant still couldn't mutate a row.

### 5. Someone with only the anon key tries to read another user's balance — through the table, and through `my_balances`.
**Stopped by:** RLS policies restrict `account_balances`/`wallet_accounts`/`ledger_entries` to `account_id in (select id from wallet_accounts where user_id = auth.uid())`; for a real anonymous request `auth.uid()` is `null`, so nothing matches, and `anon` has no grant on these tables regardless. For `my_balances` specifically: the view is created `with (security_invoker = true)`. Without that setting, a view runs with the *owner's* privileges for RLS purposes (the owner, as table owner, bypasses RLS) — so the view's own `where wa.user_id = auth.uid()` clause would be the *only* thing standing between a bug and a full cross-user leak. `security_invoker = true` makes the underlying tables' own RLS apply independently, on top of the view's filter — this is exactly the Postgres/Supabase view+RLS trap the spec points at in 5.2.

### 6. An attacker replays a captured deposit webhook 100 times.
**Stopped by:** the idempotency key for `credit_deposit` is the provider's `payment_id`. `claim_idempotency_key` does `insert into idempotency_keys(key, transaction_id) ... on conflict (key) do nothing`; only the first insert wins the unique constraint on `key` — Postgres serializes concurrent attempts on that row — every later call (even genuinely concurrent ones) is routed to the *original* `transaction_id` instead of re-crediting. Proven under real 20x-parallel replay in `scripts/prove-it.mjs` (#2).

### 7. An attacker sends a webhook with a valid old signature but a modified amount.
**Stopped by:** `verifySignature()` (`src/lib/webhook-verify.ts`) computes HMAC-SHA256 over the *raw* request body text — changing one byte of `amount_paise` changes the body, which no longer matches a signature computed over the original. This check runs *before* `JSON.parse`, so a tampered body never reaches field-level logic. Belt and suspenders: even a validly-signed webhook is credited using **our own stored** `payment_intents.amount_paise`, never whatever `amount_paise` the payload claims — the credited amount can never exceed what the user's own intent recorded.

### 8. A user double-clicks Support, then scripts 50 simultaneous sub-rupee payments from a wallet that can afford one.
**Stopped by:** `send_support` takes `FOR UPDATE` locks on the sender's, recipient's, and `platform_fee` rows — in ascending `account_id` order — before checking the balance. Postgres serializes concurrent transactions trying to lock the *same* sender row; only one proceeds at a time, re-reads the current balance, and either succeeds or raises `P1001`. No two of the 50 can both see the pre-debit balance and both succeed.

### 9. A user sends `amount_paise: -10000`.
**Stopped by three layers:** `parseAmountPaise()` (`src/lib/api-helpers.ts`) rejects non-positive/non-integer amounts before the database is touched; every RPC function independently checks `if p_amount_paise <= 0 then raise ... 'P1005'`; and even if both were bypassed, `enforce_non_negative_balance` refuses to let any account but `platform_genesis` go negative.

### 10. A user requests a withdrawal of their full balance, then immediately spends that balance before the payout settles.
**Stopped by:** `request_withdrawal`'s first money-moving statement is `available -= amount, payout += amount`, inside a transaction holding `FOR UPDATE` locks on both rows. The money is *physically moved out* of `available` in the same statement that creates the `withdrawal_requests` row — it is not a flag checked separately later. A following `send_support` call re-reads `account_balances.balance_paise` and sees the reduced number; there is no window where both operations see the pre-withdrawal balance. Proven directly in `scripts/prove-it.mjs` (#6): the follow-up send fails with `P1001` immediately after the withdrawal commits.

### 11. A user submits the same withdrawal twice, or tries to settle their own withdrawal.
**Duplicate submission:** `request_withdrawal` claims idempotency the same way `credit_deposit` does — a repeat call with the same key returns the *original* request's id and moves no additional money. Proven in `scripts/prove-it.mjs` (#7).
**Self-settle:** `settle_withdrawal`/`fail_withdrawal` are `REVOKE`d from `PUBLIC` and `GRANT`ed only to `service_role`, never `authenticated` — a user's own JWT gets a Postgres-level permission-denied before the function body runs, regardless of whether they know the `request_id`. Proven in `scripts/prove-it.mjs` (#8): a 403, `permission denied for function settle_withdrawal`.

### 12. An attacker tries to make the ledger stop summing to zero.
**Stopped by:** every RPC writes one operation's entries as a *single* multi-row `INSERT`, and `ledger_entries_balance_check` (`AFTER INSERT ... FOR EACH STATEMENT`, with a transition table) checks that every `transaction_id` touched by that statement sums to zero, immediately, before the caller ever sees a result. There is no code path that inserts a debit without its matching credit(s) in the same statement. `ledger_entries` is also append-only (#4), so a balanced ledger can't later be unbalanced by editing history.

### Weakest point, and what I'd fix first

Honestly, two things:

**1. Rate limiting is too blunt.** It's a flat hourly counter per `(user, action)`, stored in Postgres. It doesn't distinguish a single compromised account hammering many different recipients from ordinary bursty use, has no IP-based layer at all, and a patient attacker can pace requests to stay just under the cap indefinitely. I'd replace it with a proper sliding-window/token-bucket scheme and add a per-IP layer, before this went anywhere near real money.

**2. I don't fully understand a PostgREST/SECURITY DEFINER interaction I hit while building this, and that bothers me.** Mid-build, calling `credit_deposit` (a `SECURITY DEFINER` function owned by a role with full table rights) through PostgREST failed with a *table-level* permission error on `ledger_entries` for the calling role, even though the exact same call succeeded when run as a plain SQL statement with `SET ROLE service_role`. I worked around it by granting `service_role` broad direct table/function access rather than relying purely on the owner-bypass behavior of `SECURITY DEFINER`. Since `service_role` is already fully trusted server-side-only, this doesn't create a real hole here — but it means my mental model of exactly when SECURITY DEFINER's privilege bypass applies through PostgREST's call path is incomplete, and I would want to fully understand that (rather than route around it) before trusting the same pattern in a system that holds real money.

Smaller, second-tier concerns: no load test at real concurrency (thousands of simultaneous transfers) beyond the specific scenarios in the proof script; and I haven't audited every `RAISE EXCEPTION` message text for accidentally including something more sensitive than an id (the API layer never forwards raw Postgres messages to the client today, but that's a discipline, not a structural guarantee).

## Part B — What else would you do before this held real money?

- **Detecting something's already gone wrong (day one).** A scheduled job (every few minutes) running exactly the two invariant queries from the spec — `SELECT SUM(amount_paise) FROM ledger_entries` and a per-account `account_balances` vs. `SUM(ledger_entries)` diff — alerting the instant either is non-zero/non-matching. This is cheap, catches the scariest class of bug (silent drift) automatically, and needs no new infrastructure. *Before public launch:* add per-user negative-balance-would-have-occurred checks and reconciliation against the payment provider's own settlement reports (does their "total captured" match our `platform_genesis` debits?).
- **Guardrails specific to money leaving the platform (before public launch).** A daily/per-transaction withdrawal cap tighter than what any legitimate user needs day-to-day, a manual-review queue for withdrawals above a threshold or to a UPI id/bank account not seen before on that account, and a mandatory delay (even 15–30 minutes) between request and eligibility for auto-settlement, so a compromised-account drain can be caught and paused by an alert before the money actually leaves. This is the single highest-value control against real fraud, because withdrawal is the only place fraud converts into an actual, unrecoverable loss.
- **Secrets and key handling (day one, revisited before scale).** Distinct secrets per environment (local/staging/prod) that are never the same value twice; the service-role key and both webhook secrets stored in a real secrets manager (not `.env` files) once anything is deployed; documented, actually-tested rotation procedure for the webhook HMAC secrets and the service-role key, since this project currently has no rotation story at all. *At scale:* short-lived credentials / workload identity instead of long-lived static keys wherever the hosting platform supports it.
- **Database privileges (day one, this project already started this habit).** Least-privilege grants per role, reviewed on every migration — this build already caught one over-broad-by-omission case (`service_role` initially had no table grants and I had to add them explicitly) and one under-broad case (had to explicitly `REVOKE ... FROM PUBLIC` on every sensitive function, since Postgres grants `EXECUTE` to `PUBLIC` by default on `CREATE FUNCTION`). *Before scale:* a periodic automated diff of actual grants against an intended-state file, so a future migration can't silently reopen something.
- **Abuse and automated attack (day one basic version exists; harden before public launch).** The per-user hourly cap in this build is a start. Before launch: per-IP rate limiting at the edge (Vercel/Cloudflare or similar), CAPTCHA or equivalent friction on repeated auth failures, and anomaly detection on withdrawal patterns (velocity, new-destination, geographic implausibility) feeding the manual-review queue above.
- **Backups and recovery.** *Day one:* continuous WAL archiving with point-in-time recovery, not just nightly snapshots — for a ledger, "restore to last night" can mean re-losing a day of real transactions. *If the ledger were corrupted at 2am Sunday:* stop accepting new money-moving requests immediately (a feature flag, not a deploy), restore the most recent consistent snapshot to a separate instance, diff its ledger against the current one to scope exactly which transactions are affected, and only resume writes once the zero-sum invariant is manually re-verified. This is exactly why the two invariant queries above need to be routine, not just something run once during development — you want to know the moment things diverge, not discover it during a 2am incident.
- **Correcting a mistake in an append-only ledger.** Never edit or delete a row. Post a *reversing* entry — the same pattern as accounting adjustments in any real ledger system: a new transaction whose entries exactly undo the mistaken one, tagged with a `reference_type`/`reference_id` pointing at the transaction being corrected, plus a human-readable note in `audit_log` explaining why. The original mistake stays visible in history (which is the point of an append-only ledger), and the current balance is correct going forward.
- **Legal/regulatory (India).** A platform holding customer funds before disbursing them is squarely in payment-aggregator/wallet territory, which in India means RBI's Payment Aggregator (PA) authorization requirements (or partnering with an already-licensed PA rather than becoming one) and, if balances are held for any real duration, the rules around what counts as a Prepaid Payment Instrument (PPI) and PPI-issuer licensing. Practically: this is a *before public launch, not day one* item, but it needs to be raised with an actual payments lawyer before the first real rupee is accepted, not after — retrofitting compliance onto a live money system is far more expensive than designing for it up front. KYC on users (at least for withdrawal-eligible accounts) and TDS/reporting obligations on payouts also apply here.
- **The human side.** No individual should be able to move real money by hand in production without a second person's sign-off — any manual settlement/failure/refund action should require dual control (two-person approval), logged with *who* approved it, not just the automated `audit_log` actor. Deploys that touch money-moving migrations should go through review from someone other than the author, and the service-role key/webhook secrets should not be readable by anyone who doesn't need day-to-day access to production — most engineers, including me, shouldn't be able to casually read them. I'd treat "who currently has admin access to production" as something reviewed on a schedule, not something decided once and forgotten.

I would *not* build all of this on day one — a rate-limit table and the two invariant-check queries are cheap and go in immediately; the payment-aggregator conversation, dual-control tooling, and anomaly detection are real projects that belong before public launch, not before a first internal demo.
