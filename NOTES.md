# NOTES.md

**1. How do you guarantee a balance can never go negative?**
Two mechanisms, one primary and one backstop. Primary: every money-moving function takes `SELECT ... FOR UPDATE` locks on every account it touches, in ascending `account_id` order, *before* reading the balance or deciding whether the operation can proceed. If two requests against the same wallet arrive in the same millisecond, Postgres itself serializes them at the row-lock level — the second one physically cannot read the balance until the first one's transaction has committed (or rolled back), so it always sees the *post*-first-transaction balance, never a stale one. There is no way for two concurrent debits to both "see" the same starting balance and both succeed. Backstop: `account_balances` has an `enforce_non_negative_balance` trigger that rejects any `UPDATE`/`INSERT` that would leave a non-`platform_genesis` account below zero, regardless of what application logic did or didn't check — so even a bug in my own function logic can't actually persist a negative balance.

**2. You compute a 30% fee on 5 paise. What does your code produce, and why?**
`fee = floor(amount_paise * 30 / 100)`, `recipient_amount = amount_paise - fee`. For 5 paise: fee = 1, recipient = 4. I compute the recipient's share as "whatever is left after the fee" rather than as an independent 70% calculation, specifically so `fee + recipient_amount == amount_paise` is true *by construction* — there is no rounding path where both numbers are computed separately and might not add back up. Rounding the fee *down* (not to nearest, not up) means when a split can't be exact to the paise, the recipient — the person actually being paid for their work or content — keeps the remainder, and the platform's cut is what shrinks. I'd rather explain "we round in the creator's favor" than "we round in our own favor."

**3. How do you stop a user from spending money that is pending withdrawal?**
The exact moment: the `UPDATE account_balances SET balance_paise = balance_paise - amount ... WHERE account_id = <available>` inside `request_withdrawal`, which runs in the same transaction, immediately after taking a lock on that row, and *before* the function returns. There is no intermediate state where the money is "flagged" as pending while still counted in `available` — it is moved to `payout` in the same statement that creates the `withdrawal_requests` row. Nothing can slip in between the request and that moment because the whole thing is one Postgres transaction: any other operation trying to touch the same `available` row (e.g. a concurrent `send_support`) blocks on the row lock until this transaction commits, and then sees the already-reduced balance. There's no window to race.

**4. What stops a logged-in user from crediting their own wallet for free?**
Walking button-press to balance-change: (1) browser calls `POST /api/deposit/intent`; the route resolves the user from the session cookie server-side and calls `create_deposit_intent`, which only inserts a `'pending'` row — no balance code exists downstream of it. (2) the (simulated) provider — in this build, `/api/dev/simulate-provider`, itself gated behind a session check — constructs a webhook payload and signs it with `PAYMENT_WEBHOOK_SECRET`, an env var that exists only in server-side Next.js code, never in anything shipped to the browser. (3) `/api/webhooks/payment` verifies that signature against the raw request body *before* parsing any field. (4) only after that passes does it call `credit_deposit`, which is itself `REVOKE`d from `PUBLIC` and `GRANT`ed only to `service_role` — a database-level lock that exists independently of everything above it. A user would have to forge a valid HMAC without the secret *and* somehow get `service_role`-level database access to skip straight to the function; neither is reachable from the browser.

**5. Why is RLS alone not enough to stop client-side writes?**
RLS only filters/restricts *rows a role is otherwise permitted to touch* — it's a second layer on top of the base Postgres GRANT system, not a replacement for it. If `anon` or `authenticated` had been granted `INSERT`/`UPDATE` on a financial table with a *missing or wrong* RLS policy (or none at all, since RLS with zero policies means deny — but that's easy to get wrong once, e.g. by writing a policy for `SELECT` and forgetting it doesn't cover `UPDATE`), the write would go straight through. This project avoids the whole problem by never granting `authenticated`/`anon` write access to any financial table in the first place — all writes happen inside `SECURITY DEFINER` functions running as the table owner. RLS here exists purely to scope *reads*.

**6. At 3,000 concurrent users, where does this break first?**
The `platform_genesis` account row. Every single deposit across the entire platform takes a `FOR UPDATE` lock on that one row (it's the account every deposit debits from), so deposits fundamentally cannot be credited in parallel — they queue up on that one lock, one at a time, no matter how many separate users are depositing simultaneously. `platform_fee` is a similar, smaller hotspot (every `send_support`/`release_escrow` touches it). Individual users' own accounts don't have this problem — Alice's transfers don't contend with Bob's. What I'd change: split `platform_genesis` (and `platform_fee`) into N sharded sub-accounts selected by hash of some request id, with a periodic job consolidating them, so deposit throughput isn't serialized through one row — the same technique real ledger systems use for "hot" aggregate accounts.

**7. What minimum withdrawal amount did you pick, and why?**
₹100 (10,000 paise). A real payout provider charges a flat per-payout fee (often a few rupees), so anything much smaller than that risks costing the platform more to send than the withdrawal is worth. ₹100 is comfortably above that floor while still being small enough not to trap a genuine small earner's balance indefinitely.

**8. What did you use AI for, and where did you override it?**
I used Claude to write essentially all of the code in this repository, working through it step by step with heavy explanation at each stage — schema, RLS policies, the eight RPC functions, the API routes, the webhook signature verification, the UI, and the proof script. Given a hard same-day deadline partway through the build, we shifted from a fully line-by-line teaching pace to Claude writing files directly while I reviewed and tested each stage live in Studio/the browser. The most significant thing I personally caught and pushed back on mid-build was a real, reproducible bug: my first version of the zero-sum ledger check used a deferred *row-level* trigger, which passed when tested via a raw SQL session but actually failed real webhook/API traffic (`send_support` failing with a false "does not sum to zero" error) — we debugged this together down to the actual cause (row-level deferred timing behaving differently than a statement-level check) and rewrote it as a statement-level trigger with a transition table, which is what ships here. I also pushed on the SECURITY DEFINER-via-PostgREST permission failure until we had a working, understood-enough fix rather than accepting the first thing that made the error go away.

**9. What is wrong or missing in this spec?**
A few things I'd push back on: (a) the spec asks for a `users` table but doesn't say whether it should mirror `auth.users` via a trigger or be the single source of truth — I chose "mirror," which is standard for Supabase but is an assumption, not something stated. (b) it's silent on what "escrow" visibility should mean for the *worker* side (can a worker see a hold before it's released? I assumed yes, since they're a legitimate party to it, but the spec only explicitly discusses the funder's view). (c) it asks for "at least one rate limit or daily cap" but doesn't specify per-user vs per-IP vs global — a real system needs more than one axis, as I note in SECURITY.md, and picking just one (as instructed) is a real trade-off, not a complete answer. (d) the escrow `release`/`refund` functions don't have their own explicit minimum-amount rule the way withdrawal does, which felt like an inconsistency I didn't resolve either way.

**10. What did you not finish?**
Given the compressed timeline: I did not build a formal automated test suite (Vitest/Jest) beyond the required proof script — the proof script covers the required scenarios and I manually exercised every UI flow (deposit, sub-rupee send, withdraw, escrow fund/release) end-to-end in a real browser, but there's no regression suite. I did not implement `fail_withdrawal`'s or `settle_withdrawal`'s webhook path end-to-end through the UI (I verified them via direct RPC calls with a real user JWT in the proof script, not by building a "simulate payout provider" UI button the way deposit has one). Escrow refund is implemented and exercised via curl/RPC but not clicked through the browser UI the way release was. I have not written any automated tests for the UI's optimistic-update rollback path specifically (I verified it manually for one failure case, not systematically for every action). And per SECURITY.md, the rate limiting and the SECURITY DEFINER/PostgREST interaction are both things I'd want to revisit before trusting this with real money.
